更新日期：2026-10-19。执行起点：0.6.0，schema v6，公开 Git 跟踪文件 61 个。目标规模为 285～315 个有实际职责的文件，预算中值 300。阶段 A 已交付 0.7.0，schema v7，当前 78 个文件。

本文替代原 350～500 文件计划。阶段 A 标为已完成；其余未标为“已有”的能力均为待实现；阶段文件数是估算，不作为功能完成或版本发布的依据。

## 1. 交付目标与当前基线

目标是形成可以持续维护的本地账目核查产品：导入更容易纠错、异常可以批量处理、核查口径可以追溯、报告可以复核、大批次操作有明确资源边界。

0.6 执行基线已有能力：

- 标准 CSV 导入、编码和币种校验、字段映射模板、显式渠道别名。
- 人民币整数分核对、退款净额、重复证据、单边缺失与人工备注。
- 文件撤销与原子替换、输入版本、核对历史、运行差异与归档。
- 最新及历史结果分页、按需查看单个订单证据、组合筛选和全部匹配结果导出。
- SQLite 迁移、升级前备份、手动备份校验、恢复到新目录和只读诊断。
- Windows/Ubuntu × Python 3.10/3.12 CI；基线 112 项测试通过；阶段 A 后为 132 项，干净发布包可验证。

当前限制：导出 CSV 仍在内存拼装；单个订单详情仍一次返回完整源行；历史比较仍读取两次运行的全部摘要；尚无真实渠道账单样例、外部试用或生产记录。

默认保持单人本机运行和 Python 标准库依赖。没有明确需求前，不引入云账户、多租户、远程数据库或前端构建工具。

## 3. 阶段路线

每阶段独立交付可运行版本；一次只推进一个阶段。版本号为计划，发布时以实际范围确定。

| 阶段 | 计划版本 | 累计文件估算 | 本阶段净增 | 用户可见交付 |
| --- | --- | ---: | ---: | --- |
| A（完成） | 0.7.0 | 78（实际） | 17（实际） | 批量处理异常、处理冲突提示、操作记录查询 |
| B | 0.8 | 115 | 37 | 分步导入、字段诊断、模板匹配建议和标准适配接口 |
| C | 0.9 | 155 | 40 | 有版本的核查规则、按渠道统计和跨批次概览 |
| D | 0.10 | 195 | 40 | 源行分页、报告配置与流式导出 |
| E | 0.11 | 235 | 40 | 可恢复的本机任务、批次队列和 CLI 业务命令 |
| F | 0.12 | 270 | 35 | 历史比较资源优化、备份策略和性能基准 |
| G | 稳定版候选 | 约 300 | 约 30 | 无障碍与故障回归、发行工具、试用反馈闭环 |

### A：批量处理与职责拆分（已完成）

工作包：

1. 提取批次、导入和人工处理仓储及对应应用服务，保留 `Store` 兼容入口。HTTP/CLI 共享业务规则，事务由用例统一管理。
2. 结果表支持勾选当前页记录、清除选择，以及批量改为“处理中”“已处理”。第一版最多 100 条，明确展示数量，不提供隐含的跨页全选。
3. 已处理必须填写依据；金额一致记录不能被当成待处理异常；归档、输入已变或运行已变时拒绝提交。
4. 批量请求携带运行版本和每项处理版本，任一项冲突则整批回滚并提示刷新；处理版本不能只依赖时间戳。
5. 操作记录按批次分页，支持操作类型筛选；批量动作保存摘要和各项处理变更，历史运行快照保持原义。
6. 将相关页面逻辑从 `app.js` 提取到有实际调用者的处理、批次和审计模块。

验收：两标签页同时处理同一项时能识别冲突；第 N 项不合法时前 N−1 项也不写入；备注保存后刷新仍在；旧运行、归档及重复提交有明确行为；原有金额与证据规则不变。

数据设计：如需新增处理版本或审计结构，先写迁移及备份/回滚测试，再用旧库副本比对原列与原行。0.6 生成的历史快照不得被当前处理回填改写。

### B：导入向导与标准适配框架

工作包：编码/表头/映射/别名/币种校验按职责提取；建立标准 CSV 适配协议及注册入口；导入向导分为文件、映射、整份校验、确认四步；模板仅给出候选，须人工确认；错误列表分页并可下载。

解析与预览必须共用相同规则；相同字节、不同映射/别名的冲突继续要求替换。错误导出只留在用户本机。预览标识须绑定文件指纹、映射和适配版本，避免确认时使用另一份输入。

验收：前导零、多行引号、BOM、GB18030、后续行币种错误和错误列映射均可定位；任意校验失败时整份不写入；替换失败仍保留原有效输入；现有标准 CSV 保持兼容。

### C：规则版本、统计与工作台

工作包：核查配置采用不可变修订；记录每次运行使用的规则版本；增加渠道汇总、异常类型计数、当前处理进度与跨批次概览；支持保存常用筛选。

首批可配置项限定为明确的异常展示策略和人工确认的金额容差。默认容差为零；容差命中必须单独标注，不改写实际差额，不把重复流水、币种错误或单边缺失解释为金额一致。规则变更要求生成新运行，不覆盖旧结果。

汇总须说明口径：按运行金额统计与当前处理进度分别标注，跨批次重复输入不自动视为独立经营收入；多个异常类型的计数可重叠，不要求相加等于订单数。

验收：同输入不同规则生成可比较版本；旧规则和历史数值可复核；统计与相同筛选下明细一致；缺失规则版本的旧运行明确显示旧版口径。

### D：证据与报告

工作包：单订单源行分页；可选择列与顺序的报告配置；导出展示运行、规则和筛选条件；使用分块读取和写出生成完整 CSV；提供打印友好的 HTML 核查报告。

报告配置是展示配置，不能改变核对结果。导出固定运行并明确处理状态快照语义，避免各块读取到不同备注；响应开始前完成参数与版本检查。断开连接后关闭游标、事务和临时文件。继续保留 BOM、中文编码和公式转义。

验收：一个订单包含大量源行时单次详情返回有上限；导出全部匹配记录且无重复/遗漏；导出期间修改备注不会形成无法解释的混合快照；取消下载能释放资源；旧报告配置可识别版本。

### E：本机任务与 CLI

工作包：对已有核对/报告用例增加本机任务记录、进度、取消和失败原因；批次队列按配置顺序执行；增加批次列表、导入、核对、状态查看、报告导出的 CLI 命令。

只建设当前操作需要的本机执行器。任务提交、执行中、完成、失败和取消有明确状态转换；进程退出后的未完成任务在重启时可识别，恢复或重试必须幂等。取消只能在安全检查点生效，已经提交的业务事务不伪装为撤销。

验收：重复提交不产生重复运行或覆盖报告；执行中退出与重启有可复现结果；HTTP 和 CLI 使用同一校验；归档及版本变化在执行时重新检查；用户可看到明确进度和错误。

### F：性能与本地运维

工作包：以结果摘要索引优化历史比较，避免完整加载两次运行；建立可重复的合成性能基准；支持经用户配置的启动备份及备份保留策略；检查未完成任务和本产品临时文件。

性能基准覆盖 5 千、2 万、10 万分组，多文件输入遵守既有单文件上限。记录环境、耗时、峰值内存、SQL 查询量和响应大小，先测基线再制定门槛；超大样本不强塞每次 CI。备份清理只处理本产品明确登记的备份，至少保留一份校验通过的恢复点；未知文件不删除。

验收：比较页和导出资源消耗符合已记录预算；备份失败不删除旧恢复点；清理失败可解释并可重试；数据库损坏和未来版本不被自动修复覆盖。

### G：稳定版候选与交付

工作包：关键流程键盘操作、焦点与窄屏；断网本地使用；HTTP 参数/路径/来源检查回归；干净安装、升级、回退和发布工具；贡献指南与问题模板；真实试用反馈与修复关联。

这一阶段按缺陷和实际试用补齐文件，不预生成客户档案或无内容的说明。没有外部试用证据时，可以交付本地候选版，但不宣布已经通过客户验收。

稳定 1.0 的额外门槛：至少一个真实渠道格式经过明确版本、实际输入和人工期望结果验证；完整导入、处理、报告与恢复经过外部实际使用反馈。缺少这些证据时继续发布 0.x 或候选版本，文件数不触发 1.0。

## 4. 渠道适配候选工作

真实渠道适配取得样例后单独排期，不阻塞 A～F 的标准 CSV 改进；新增适配器时重新核对对应阶段的文件预算。

取得实际样例后，先核对当时有效的官方格式，再单独排期：

1. 说明格式版本、文件类型、说明/汇总行、编码与支持范围。
2. 明确订单号、收款、退款、流水号和渠道字段；识别不了的版本拒绝导入。
3. 固定适配器版本和来源行号，保留可追溯的标准化结果。
4. 使用人工核对表验证金额与异常，并与标准 CSV 行为做契约回归。
5. 在对应阶段预算中替换一部分通用扩展，不为凑规模同时开多个空适配器。

遵循用户的公开提交规则：真实账单、敏感文件和内部记录从提交清单删除；不通过脱敏后提交来保留这些文件。公开 fixture 仅使用独立编写的合成输入，并明确不代表真实渠道验收。私有样例的验证结论只在本机记录。

## 5. 架构落点

| 目录 | 责任 | 约束 |
| --- | --- | --- |
| `ledgerdesk/domain/` | 金额、核对、处理状态、规则与统计口径 | 不依赖 HTTP、SQLite 或页面 |
| `ledgerdesk/application/` | 导入、批量处理、报告、任务等用例 | 统一事务和幂等语义 |
| `ledgerdesk/persistence/` | 仓储、查询、迁移、备份 | 不向 HTTP 泄漏原始连接 |
| `ledgerdesk/ingestion/` | 读取、预览、映射与整份校验 | 不改变现有输入契约 |
| `ledgerdesk/adapters/` | 已实际实现的输入适配器 | 先有协议和使用者，再提取通用结构 |
| `ledgerdesk/http/` | 分功能路由、请求与错误响应 | `server.py` 保留启动兼容入口 |
| `ledgerdesk/cli/` | 业务命令及输出 | `__main__.py` 保留命令入口 |
| `ledgerdesk/static/` | 按实际页面功能组织 JS/CSS | 保持无需前端构建即可运行 |
| `tests/` | 业务、事务、HTTP、迁移、并发及故障测试 | 按行为组织，允许参数化，禁止一用例一文件凑数 |
| `samples/`、`docs/`、`scripts/` | 合成示例、公开契约、工程工具 | 显式发布清单，排除所有本机业务内容 |

新增 Python 子包注意 unittest 发现规则与初始化要求；旧测试搬迁前后都核对发现数量和关键用例，避免目录重组造成测试悄悄消失。

## 7. 每次发布的质量门槛

- 与本次行为和风险相关的回归通过；完整测试在 Python 3.10/3.12 与 Windows/Ubuntu CI 通过，新增 JS 完成语法检查。
- 有数据库变更时，迁移前备份、失败回滚、高版本拒绝、完整性和外键检查、旧库副本原数据逐表比对通过。无迁移时不为凑流程重写默认库。
- 浏览器验证用户可见的新增路径，包括错误状态与窄屏；合成操作只在隔离数据目录执行。
- 新文件加入显式发布清单；干净包可测试，源文件与包内容逐字节一致。
- 提交与发布包不包含真实 CSV、数据库、备份、密钥、个人路径、内部交接或验证记录。
- 版本、变更说明、契约和实际行为一致；同步两个远程并确认 CI。
- 记录阶段交付、实际文件数、未解决限制和下一项，不把计划写成已完成。
