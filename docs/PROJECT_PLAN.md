# LedgerDesk 项目扩展计划

版本路线：0.3.0 → 1.0.0（0.4 首批及 0.5 本地数据保护已完成）

计划日期：2026-10-18

## 一、计划目标

计划编制时，LedgerDesk 是一个本机运行的订单与支付账单核查工具，公开源码基线为 25 个文件（计划书加入后为 26 个），核心流程已经覆盖：标准 CSV 导入、人民币金额核对、重复和单边数据识别、人工处理、历史运行、文件撤销与替换、模板、渠道别名和报告导出。

下一阶段的目标是把它发展成一个结构清晰、可以持续维护、适合真实小团队试用的本地账目核查产品。目标文件规模约为 350～500 个有实际职责的文件，500 只是工程规模结果，不是单独的交付指标。

计划结束时应达到：

- 支持可插拔的账单渠道适配器，并至少完成一个经过真实格式核对的渠道适配器；
- 可以管理导入模板、渠道别名、核查历史、批次状态和报告版本；
- SQLite 数据可以迁移、备份、恢复和诊断；
- 核心金额和核查规则有完整的单元、集成、回归和金样测试；
- 页面、CLI、API 和文档使用同一套业务契约；
- 公开仓库具备许可证、CI、发行说明和贡献入口；
- 真实试用、反馈和修复记录如实保存，不虚构客户或生产经历。

## 二、基本原则

1. 文件数量服从产品边界。不得为了达到数字拆空模块、复制测试、制造假客户文档或把一段代码机械拆成很多文件。
2. 每一个新功能都要有业务理由、输入输出契约、测试和用户可见的完成标准。
3. 数据库迁移必须有版本号、升级前备份、失败回滚和旧库副本验证。
4. 核查结果必须保留输入版本、源文件指纹、规则版本和处理证据。
5. 渠道适配必须基于明确版本的官方格式和实际样例，不能把一个示例声称为所有微信或支付宝账单的通用适配。
6. 本地测试、个人自测、外部试用、付费交付和生产运行分开记录。
7. 默认优先本机可用性和数据可控性，暂不建设云端多人系统。

## 三、目标架构

### 1. domain

放置订单、支付事件、退款、批次、核查结果、处理状态、差异类型和金额对象。领域层不依赖 HTTP、SQLite 或页面。

计划拆分：

- `money`：分、元、格式化、舍入和边界；
- `orders`：业务单模型和业务键；
- `payments`：收款、退款和流水约束；
- `reconciliation`：分组、净额、差异和证据；
- `reviews`：处理状态、备注和证据版本；
- `batches`：批次生命周期和来源元数据。

### 2. ingestion

统一处理输入文件、编码、表头、字段映射、币种、渠道别名和适配器。

- CSV 基础读取器；
- 字段候选和冲突报告；
- 映射模板；
- 渠道别名；
- 文件限制和错误行；
- 适配器注册表；
- 导入预览和整份事务校验。

### 3. adapters

每个渠道适配器都必须拥有自己的解析器、字段规则、样例、错误用例和版本说明。

建议顺序：

1. 标准 CSV 适配器继续作为基准；
2. 一个明确版本的微信账单适配器；
3. 一个明确版本的支付宝账单适配器；
4. 其他渠道按真实需求增加，不预先建设空适配器。

### 4. persistence

把当前 `store.py` 拆为数据库连接、迁移、仓储、备份、审计和查询服务。

- schema migration；
- batch repository；
- import repository；
- run repository；
- review repository；
- template repository；
- backup and restore；
- integrity diagnostics。

### 5. application

提供创建批次、导入、撤销、替换、核对、重跑、比较、备注、导出和诊断等用例服务。HTTP 和 CLI 只负责解析输入、调用用例和格式化结果。

### 6. presentation

页面逐步拆成批次列表、导入向导、结果表、详情面板、历史比较、模板管理、备份管理和诊断页面。当前仍可保持无构建工具，但页面逻辑必须按功能模块组织。

### 7. verification

测试按目的分层：

- `unit`：金额、映射、别名、差异规则；
- `integration`：SQLite、迁移、导入事务、HTTP；
- `golden`：真实格式的脱敏样例和期望结果；
- `regression`：每次修复的最小复现；
- `property`：金额守恒、重复输入和顺序变化；
- `browser`：关键页面操作和响应式布局。

## 四、版本路线

### 0.4：领域拆分和配置稳定化

2026-10-19 进度：已完成领域规则、核对服务、迁移/备份、模板及运行仓储的第一批拆分，保留兼容入口；补齐筛选导出、别名变更与历史校验，新增模板文件管理、标签/归档和 JSON 配置。批次与导入剩余事务暂留在兼容入口中，后续按职责继续提取。

目标：降低单体文件耦合，保持 0.3.0 行为不变。

工作内容：

- 拆分金额、订单、支付事件和核查结果模型；
- 拆出数据库迁移和仓储层；
- 统一 API 错误码和输入错误结构；
- 增加批次标签、归档状态和批次摘要；
- 增加映射模板删除、复制、导入和导出；
- 增加配置文件格式和默认配置检查；
- 为拆分后的领域层补单元测试。

验收：0.3 的 62 项基线测试全部通过，新增模块不直接依赖 HTTP，旧数据库可在副本中升级，页面主要路径不回退。

### 0.5：本地数据保护（已调整交付）

2026-10-19 进度：现有仓库只有标准格式的合成账单，缺少真实渠道样例。为避免把推测格式当成完成适配，本轮先交付原计划 0.7 中的备份列表、备份校验、恢复到新目录、只读诊断和 CLI，沿用 schema v5。自动轮换和远程备份未纳入本轮。原定渠道适配保留为下面的独立里程碑，取得样例后再排入版本。

### 待样例里程碑：一个真实渠道适配器

目标：完成一个有明确格式版本和脱敏样例的渠道适配器。

工作内容：

- 固定官方格式版本和字段契约；
- 解析编码、表头、金额、收款、退款、订单号和流水号；
- 对账单说明、汇总行、空行和非交易行做明确处理；
- 保存原始行号和适配器版本；
- 增加金样文件、错误样例和兼容性测试；
- 在页面中显示适配器名称和版本。

验收：脱敏样例可重复导入，字段和金额结果与人工核对表一致；未知版本明确拒绝或降级为标准 CSV 预览。

### 0.6：历史、报告和批量操作

目标：让用户可以解释一次核查如何变化，并处理较大的批次。

工作内容：

- 历史运行摘要和差异对比；
- 新增、消失、金额变化、异常变化和处理状态变化；
- 当前筛选导出、全部导出和报告模板；
- 服务端分页和详情按需加载；
- 批量标记处理中、批量导出和批量归档；
- 汇总图表和按渠道统计。

验收：同一批次两次运行可以准确解释变化；大于 5000 个订单分组时页面不会一次渲染全部源行；导出版本和筛选条件可追溯。

### 0.7：数据保护和运维工具

目标：降低本地数据丢失、错误恢复和诊断成本。

工作内容：

- 备份列表、备份校验和恢复到新数据目录；
- 数据库完整性检查和可读诊断报告；
- 导入、核对、迁移和导出操作日志；
- 崩溃后安全启动和临时文件清理；
- 大文件导入性能测试；
- 版本升级提示和回滚说明。

验收：备份文件可在新目录启动并保留结果、备注和审计记录；损坏或高版本数据库不会被静默覆盖。

### 0.8：真实试用准备

目标：让外部试用可以留下可验证的反馈，而不引入不必要的云服务。

工作内容：

- 试用数据说明和脱敏工具；
- 反馈模板、问题编号和修复关联；
- 明确的产品边界和数据保留说明；
- 一键导出诊断包，默认排除 CSV 原文和个人数据；
- 试用验收清单和版本回退说明。

验收：试用方可以在本机完成导入、核对、处理、导出和备份；反馈可以关联到具体输入、版本和修复提交。

### 1.0：稳定本地交付版

目标：完成一个经过持续试用验证的本地版本。

必须满足：

- 至少一个真实渠道适配器经过实际样例验证；
- 关键流程有稳定的自动测试和浏览器回归；
- 迁移、备份、恢复和导出有明确操作说明；
- 公开仓库 CI 全绿，发行包可从干净目录验证；
- 真实使用反馈、问题和修复记录完整；
- 不把个人测试或合成样例描述为客户验收或生产记录。

## 五、文件规模预算

下表是工程结果的预算，不是必须填满的指标：

| 类别 | 当前 | 目标范围 |
|---|---:|---:|
| 领域和应用代码 | 8 | 50～75 |
| 持久化、迁移和工具 | 1 | 30～45 |
| 输入与渠道适配器 | 2 | 50～100 |
| 页面和静态资源 | 3 | 45～75 |
| 测试、样例和 fixture | 5 | 130～190 |
| 文档、CI、配置和脚本 | 6 | 35～55 |
| 合计 | 25 | 335～540 |

达到 500 个文件的合理来源应是：多个真实适配器、分层测试、脱敏金样、历史和运维工具，以及能被维护的文档。生成文件、重复测试和空目录不计入计划。

## 六、质量门槛

每个版本必须满足：

- Python 3.10 和 3.12 自动测试通过；
- 前端语法检查通过；
- SQLite integrity_check 和 foreign_key_check 通过；
- 旧库副本迁移前后原数据逐表比对；
- 发布包解压到干净目录后可以运行测试；
- 不能把本地数据库、备份、上传 CSV 或诊断包打进源码发布包；
- 所有新增业务规则有正例、反例和回归测试；
- 文档中的版本、功能和验证结果与代码一致。

## 七、近期 30 天执行顺序

1. 给 0.3.0 的模板、别名和历史比较补齐 API 与浏览器回归。
2. 拆出 `domain` 和 `persistence` 的第一批模块，保持外部行为不变。
3. 选择一个官方渠道格式，收集并脱敏一份真实样例。
4. 设计适配器接口和金样测试，不直接改现有标准 CSV 规则。
5. 增加备份列表、恢复到新目录和诊断命令。
6. 补 README 截图、贡献指南、Issue 模板和发布说明。
7. 每周记录实际使用、发现的问题和修复提交，作为后续版本依据。

## 八、暂缓事项

在出现明确需求和数据前，暂缓云部署、多人账户、权限系统、自动拉账、手续费结算、多币种汇兑和大规模异步任务。它们会显著扩大安全、运维和数据责任范围，当前的个人本地产品还没有足够证据支撑这些投入。
